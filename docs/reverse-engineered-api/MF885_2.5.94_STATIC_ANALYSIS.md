# MF885 firmware 2.5.94 — static analysis baseline

This document records the reproducible static-analysis baseline for the stock ZMI MF885 firmware used by this project. It separates facts established from the exact 2.5.94 image from assumptions inherited from related firmware.

## Executive conclusions

1. The analysed image is a complete stock MF885 BackupFw image, not a reconstructed approximation.
2. The main runtime is a Nucleus PLUS / Marvell monolithic image (`OSLO`), not a conventional Linux filesystem/userland.
3. The XML/Duster management interface is real native firmware machinery. XML schemas, frontend code and native callback descriptors must all be considered separately.
4. The `reset` model is semantically a **reboot**. It is distinct from `restore_defaults`, which is the factory-default path.
5. The `poweroff` model carries a `shutdown` contract.
6. Static evidence does **not yet prove the exact side-effecting HTTP method on stock 2.5.94** strongly enough to enable a destructive client command. Older reverse-engineering notes point to command-on-read GET, while the current project client uses POST/SET. Until that transport discrepancy is closed, the 2.5.94 profile must remain destructive-disabled.
7. `Restart` and `reboot` are not two firmware operations. `Restart` is UI wording for the reboot operation; `reset` is the firmware model name.

## 1. Exact analysed artifact

Golden stock BackupFw:

```text
size    8,323,644 bytes
sha256  2b5880fc26805918bb574d07341ea9b863f8261be34c3bf9766fac0929204531
```

Decompressed stock OSLO:

```text
size    9,648,064 bytes (0x9337c0)
sha256  d51fb378d8ccf68662174f39d6b8c4f6be5571280790bc3a4dc4a9e8a967078c
```

The same raw OSLO fingerprint is asserted by the project's staged build tooling before applying native patches, so offsets derived from it are anchored to the exact golden image rather than to a related release.

## 2. Backup container / partitions

The stock BackupFw image uses the ZIMI backup format with a 572-byte header followed by fixed partitions used by the device's restore path.

Known layout:

```text
OSLO  0x460000
GRBI  0x0c0000
WEBI  0x1c0000
WIFI  0x080000
WCAL  0x080000
RFBN  0x010000
```

The reverse-engineering toolchain has repeatedly performed exact OSLO LZMA decompression/recompression round trips while preserving the partition checksum expected by the unchanged ZIMI header. That work is useful here because it independently validates the boundaries and exact raw OSLO baseline.

A BackupFw/RestoreFw image should not be confused with the signed Marvell FBF software-update path. They are distinct firmware-delivery mechanisms.

## 3. Runtime architecture

The main OSLO image contains:

- Nucleus PLUS RTOS components;
- Marvell networking and cellular integration;
- a forked lwIP networking stack;
- Mongoose 3.0 HTTP server code;
- Digest-authentication and session logic;
- Duster XML model dispatch;
- SMS/SIM/APN/cellular management;
- NAT, DHCP, DNS, firewall/routing functions;
- firmware backup/update/restore code;
- CWMP/TR-069 and STUN-related management;
- Wi-Fi driver/WPS/client-related code.

This matters operationally: paths such as `/etc/init.d/...` found as strings are legacy/product-tree artifacts and do not imply a Linux shell or an executable shell-script filesystem on this build.

## 4. Duster XML model dispatcher

Exact 2.5.94 native analysis established a 0x38-byte Duster model descriptor layout. Relevant callback slots are:

```text
+0x10  native pre_set
+0x18  native post_set
+0x20  native pre_get
+0x28  native post_get
```

The callback dispatcher is present in the exact raw OSLO, and the active model registry is consumed by native lookup/dispatch code.

This creates a critical rule for reverse engineering command-like models:

> An XML schema proves the data tree, but it does not by itself prove whether GET, SET, pre-GET, post-GET, pre-SET or post-SET is the side-effecting operation.

That rule is the reason destructive commands are held to a higher evidence standard than read-only models.

## 5. HTTP/Digest transport

The physical XML endpoint used by the current project/device family is:

```text
/xml_action.cgi
```

Normal Duster forms are:

```text
GET  /xml_action.cgi?method=get&module=duster&file=<model>
POST /xml_action.cgi?method=set&module=duster&file=<model>
```

The family has a Digest-authentication quirk: the physical request path and the URI used in the Digest calculation/Authorization header are not always identical. The project handles that separately in its authentication layer.

For ordinary state changes the safe client pattern is POST/SET followed by read-back verification. Command-like power models are special because the request itself can terminate connectivity before a response is returned.

## 6. WEBI comparison: 2.5.94 versus 2.5.96

The two analysed web payloads are extraordinarily close:

```text
paths in WEBI            320 / 320 identical names
byte-identical files     319 / 320
stock differing file     www/data/4_apn.txt
```

The analysed GRBI, WIFI, WCAL and RFBN partitions are also byte-identical between the two images.

However, native OSLO is not interchangeable:

```text
2.5.94 raw OSLO  9,648,064 bytes
2.5.96 raw OSLO  9,648,128 bytes
size delta       +64 bytes
```

After accounting for the known insertion, roughly 16.35% of raw OSLO bytes still differ. ASCII string sets are about 99.846% similar, which explains why the products look nearly identical from the frontend while still requiring firmware-specific native offsets and callback proof.

Conclusion: WEBI contracts can be compared with high confidence, but destructive native behaviour must not be copied solely by offset or by analogy.

## 7. Reboot: `reset` model

The stock XML contract is:

```xml
<RGW><reboot/></RGW>
```

Model name:

```text
reset
```

Semantic conclusion:

```text
reset model  -> reboot/restart router
```

This is **not** a factory reset. Factory defaults are represented by the separate `restore_defaults` model.

This distinction is strong enough to call the model semantics firmware-confirmed.

### Transport confidence

The remaining issue is how the stock 2.5.94 backend is intended to trigger the side effect.

Evidence currently preserved in the research set is mixed:

- the generated schema inventory exposes the ordinary generic Duster GET and SET forms;
- an earlier static API reference identifies power models as command-on-read and gives `GET ...&file=reset` as the stock-style trigger;
- the current application implementation for confirmed 2.5.96 power operations uses POST/SET plus the XML tree;
- there is no preserved stock 2.5.94 packet capture or sufficiently explicit exact-2.5.94 reset-descriptor callback decode in the repository that proves one method and excludes the other.

Therefore the correct confidence split is:

```text
model exists                 confirmed
model means reboot           confirmed
reset != factory reset       confirmed
exact 2.5.94 trigger method  not yet runtime-confirmed
```

The project must not infer a destructive trigger from the model name alone.

## 8. Shutdown: `poweroff` model

The stock XML contract is:

```xml
<RGW><shutdown/></RGW>
```

Model name:

```text
poweroff
```

The combination of schema and firmware model naming is strong evidence that this is the router shutdown path.

As with `reset`, the remaining uncertainty is the exact side-effecting GET/SET transport on stock 2.5.94. It should remain disabled in the compatibility profile until independently verified.

## 9. `trueshutdown`

A `trueshutdown` model/schema is present in the broader analysed firmware family. Static evidence has not established a sufficiently useful and safe behavioural distinction between it and `poweroff`.

Project policy:

```text
trueshutdown = unadvertised / unconfirmed
```

Do not probe guessed values merely because the schema exists.

## 10. `restore_defaults`

`restore_defaults` is separate from `reset`.

This distinction is safety-critical:

```text
reset             -> reboot semantics
restore_defaults  -> factory-default semantics
```

Client UI or code must never label `file=reset` as “factory reset”, and must never substitute `restore_defaults` when implementing Restart/Reboot.

## 11. What “Restart” means in this repository

The current dashboard uses three names at different layers:

```text
UI label          Restart
client action     reboot
firmware model    reset
XML semantic      reboot
```

They describe one logical router-restart operation. There is no separate firmware “Restart” command in addition to “Reboot”.

For a firmware profile with a confirmed transport, the mapping should be read as:

```text
Restart -> reboot action -> reset model -> reboot firmware operation
```

## 12. Why 2.5.94 destructive controls remain disabled

The 2.5.94 profile currently contains:

```text
destructive: {}
```

After this analysis that remains the correct implementation choice, but for a more precise reason than before.

It does **not** mean the power models are absent. Their schemas and semantics are known. It means the exact side-effecting transport has not passed the project's confirmation threshold for this build.

Enabling the current POST-based client path just because 2.5.96 uses it would erase the distinction between firmware-confirmed semantics and firmware-confirmed invocation.

## 13. Wi-Fi / STA findings relevant to firmware identity

The exact 2.5.94 image was also used for deep Wi-Fi reverse engineering, which provides independent confidence that the raw image has been analysed beyond string extraction.

Findings include:

- shipped `sd8801_uapsta.bin` Wi-Fi firmware;
- WPS/STA-related code and scan/association strings in OSLO;
- explicit `BSS_TYPE_STA` and `BSS_TYPE_UAP` paths in WPS-related code;
- product networking that registers the uAP side with lwIP;
- exact Duster descriptor analysis showing `wlan_cli_scan` schema/storage paths can exist without an active native scan callback;
- later native analysis showing the product `mlan_ops[]` registration is UAP-only, preventing a simplistic “enable STA with one flag” approach.

These findings reinforce the central methodology: presence of schema/string/library code is not equivalent to a live product capability.

## 14. Network / cellular findings

The exact raw 2.5.94 image contains the native networking and modem paths used by the project's staged research, including:

- IPv4 NAT forwarding path used for TTL research;
- stock AT transport used for controlled modem diagnostics;
- MRD/IMEI-related strings and handlers;
- APN/WAN data-model machinery;
- `status1`, `wan`, and `Engineer_parameter` data used by the application's read-only diagnostics.

Modified community-build capabilities are not automatically properties of stock firmware. They are documented separately and must not be described as stock API features.

## 15. Debug, diagnostic and Telnet evidence

The firmware family contains schemas and strings for engineering/debug facilities including `debugmodeon`, `diagnostic`, and `control_telnet`.

The existence of those contracts does not prove a general-purpose shell:

- `diagnostic` may have a schema while native callback slots are inactive in a stock build;
- a Telnet-enable field does not prove a listening Telnet daemon;
- the platform is Nucleus-based, so Linux assumptions such as BusyBox/Dropbear `/bin/sh` must not be made without direct evidence.

The project therefore treats these features as firmware/profile-specific experiments rather than portable APIs.

## 16. Firmware backup / restore observations

Static analysis identified separate backup/restore and normal firmware-update mechanisms. Configuration/firmware backup endpoints can expose highly sensitive device state and should be treated as secrets.

For destructive experimentation, the exact golden BackupFw fingerprint above is the reference recovery artifact. A successful checksum or HTTP response is not a substitute for runtime recovery testing.

## 17. Confidence matrix for power controls

### Reboot / Restart

- XML schema present: **yes**
- firmware model present: **yes**
- semantics (`reset` means reboot): **yes, firmware-confirmed**
- distinct from factory reset: **yes**
- exact 2.5.94 side-effecting HTTP method: **not yet independently confirmed**
- safe to expose in current 2.5.94 project profile: **no, not yet**

### Power off

- XML schema present: **yes**
- firmware model present: **yes**
- semantics (`poweroff` / `shutdown`): **strong static evidence**
- exact 2.5.94 side-effecting HTTP method: **not yet independently confirmed**
- safe to expose in current 2.5.94 project profile: **no, not yet**

### True shutdown

- family schema/model evidence: **yes**
- behavioural semantics versus `poweroff`: **unresolved**
- safe to expose: **no**

### Restore defaults

- separate model: **yes**
- factory-default semantics: **yes**
- interchangeable with reboot: **no**

## 18. What would close the remaining power-command gap

Any one of the following, tied to the exact 2.5.94 build, would materially upgrade transport confidence:

1. a packet capture of the stock WebUI issuing reboot/shutdown;
2. an exact native descriptor decode for `reset`/`poweroff` showing the active callback direction and handler;
3. a controlled live test of the candidate transport with before/after boot identity and configuration-preservation checks.

Until then, documentation should say **“command semantics confirmed; trigger transport unconfirmed”**, not “unsupported” and not “fully supported”.

## 19. Project implementation consequence

No code change is justified merely by discovering the schemas: the existing 2.5.94 profile should continue to suppress destructive controls at the backend boundary.

If/when the transport is confirmed, the compatibility profile should encode the transport explicitly rather than relying on a global POST assumption. That will allow 2.5.94 and 2.5.96 to differ safely if necessary.
