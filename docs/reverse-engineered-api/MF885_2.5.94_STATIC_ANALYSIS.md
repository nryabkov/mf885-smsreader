# MF885 2.5.94 static analysis

This document records firmware-specific findings for the clean ZMI MF885 / MF96 Ver.D 2.5.94 image used by this project. It exists so that 2.5.94 capabilities are not inferred from the neighbouring 2.5.96 build.

## Analysed image and provenance

Target hardware: **ZMI MF885 / MF96 Ver.D**.

Firmware lineage: `2.5.94_release_MF855_NZ_CP_2.129.003`; the device-facing firmware version is `2.5.94`.

Clean golden `BackupFw` image:

- size: `8,323,644` bytes;
- SHA-256: `2b5880fc26805918bb574d07341ea9b863f8261be34c3bf9766fac0929204531`;
- two consecutive post-reboot backups were byte-identical.

Decompressed OSLO runtime image:

- size: `9,648,064` bytes (`0x9337c0`);
- SHA-256: `d51fb378d8ccf68662174f39d6b8c4f6be5571280790bc3a4dc4a9e8a967078c`;
- runtime base used by the native reverse-engineering work: `0x06000000`.

An earlier backup contained one all-zero `0x10000` span inside OSLO. That image is not used as evidence or as a recovery image; all findings below refer to the clean golden image above.

## Runtime architecture

The main runtime is a monolithic ARM little-endian **Nucleus PLUS RTOS** image rather than a conventional Linux root filesystem. It contains the Marvell networking/modem stack, lwIP, the Duster XML model layer and an embedded **Mongoose 3.0** web server.

Consequences for API work:

- an administrator login is not a Unix shell;
- XML models are firmware RPC/data-model contracts, not REST resources;
- a schema alone is insufficient evidence for a callable handler;
- destructive commands must be scoped to an exact firmware profile.

## Backup image / flash layout

The live `BackupFw` result is a ZIMI backup container, not the public Marvell FBF update package. The normal partition payload sizes are:

- `OSLO`: `0x460000`;
- `GRBI`: `0x0c0000`;
- `WEBI`: `0x1c0000`;
- `WIFI`: `0x080000`;
- `WCAL`: `0x080000`;
- `RFBN`: `0x010000`.

Native analysis also recovered normal and recovery flash mappings. Recovery partitions exist, but the exact guaranteed entry/fallback mechanism has not been proven, so their presence must not be treated as a brick-proof recovery guarantee.

The native `RestoreFw` path validates ZIMI metadata, hardware/version information and additive checksums before erasing/writing partitions. No RSA signature verification was identified on this ZIMI restore path. This is a static finding, not a recommendation to upload modified images.

## WEBI and relationship to 2.5.96

The clean 2.5.94 and analysed 2.5.96 WEBI payloads have:

- the same `320` filenames;
- the same `123/123` XML schema files;
- the same `51/51` JavaScript files;
- `319/320` files byte-identical;
- the only observed stock WEBI difference is `www/data/4_apn.txt`.

Native OSLO must **not** be assumed byte-compatible: after accounting for a known 64-byte insertion, the raw images still differ substantially. The common ASCII string set is nevertheless very close (81,117 common strings; Jaccard similarity about 99.846%).

This distinction is important: WEBI/XML contracts can be compared directly where files are byte-identical, while native function addresses and enum values remain firmware-specific.

## XML transport and authentication

The physical HTTP endpoint used by the live device/project is:

```text
/xml_action.cgi
```

Normal model requests use:

```text
GET  /xml_action.cgi?method=get&module=duster&file=<model>
POST /xml_action.cgi?method=set&module=duster&file=<model>
```

HTTP Digest has a vendor quirk: the Authorization `uri` and HA2 for XML calls use `/cgi/xml_action.cgi` even though the actual request path is `/xml_action.cgi`.

This split is confirmed by the working 2.5.94 client and must be preserved by generated clients/specifications.

## Reboot / restart — firmware-specific result

### Static contract

The 2.5.94 WEBI contains the `reset` XML model with this tree:

```xml
<RGW><reboot/></RGW>
```

The consolidated API inventory, built from the firmware schemas/native analysis and checked against 2.5.94 behaviour, classifies `reset` as a **confirmed write-command**.

The corresponding model write is:

```http
POST /xml_action.cgi?method=set&module=duster&file=reset
```

with an XML body equivalent to:

```xml
<RGW><reboot></reboot></RGW>
```

`<reboot/>` and `<reboot></reboot>` are XML-equivalent for this empty element.

### It is not factory reset

`restore_defaults` is a separate firmware model. Therefore `file=reset` + `RGW/reboot` is the reboot path and must not be described as a factory-default reset.

### Client semantics

In this project the visible UI label **Restart** maps to the internal action `reboot`, which maps to compatibility operation `reset`, model `file=reset`, tree `reboot`.

So there are not two different device operations named “Restart” and “Reboot”:

```text
Restart (UI) -> reboot (client action) -> reset (firmware model) -> RGW/reboot
```

### Response handling

A reboot can tear down Wi-Fi/HTTP before a final response is returned. The client must therefore:

- submit the destructive request once;
- not automatically replay it after a 401 or connection loss;
- treat an early connection drop as an indeterminate/submitted result rather than a definite failure;
- optionally poll safe status reads until the router becomes reachable again.

The current `api-contract.js` destructive path follows this rule by setting `retry401: false`.

**Verdict for MF885 2.5.94: firmware-confirmed.** The repository may advertise the reboot mapping for the 2.5.94 profile.

## Power-off and `trueshutdown`

The shared 2.5.94 WEBI contains a `poweroff` schema rooted at `RGW/shutdown`, and native research found power-control model names including `poweroff` and `trueshutdown`. However, the exact externally safe trigger/semantic distinction has not been established to the same standard on the target 2.5.94 device.

Therefore this analysis does **not** promote 2.5.94 `poweroff` or `trueshutdown` to an enabled compatibility-profile operation. Presence remains useful reverse-engineering evidence, but destructive client support stays disabled until the exact write contract/effect is independently confirmed.

## Status, WAN and LTE telemetry

Live 2.5.94 fixtures in this repository confirm the firmware-scoped interpretation used by `zmi-mf885-2.5.94`, including:

- `sys_mode=17` as LTE in the captured MF885 state;
- SIM `1` as ready;
- registration `1` as home registration;
- roaming `0` as home network;
- PDP state `1` as connected;
- PDP type `IP` as IPv4;
- `signalbar` values 0–5.

Unknown numeric values are deliberately left raw rather than borrowed from 2.5.96.

`Engineer_parameter` exposes the stock radio telemetry required for band, EARFCN, PCI, cell ID, TAC, RSRP, RSRQ, SINR/CQI and related diagnostics; no native patch is needed for those reads.

## SMS and traffic

The stock `message` model provides the SMS list/send/delete/read command machinery used by this project. The web UI pages SMS in small batches, so the project walks pages defensively and deduplicates results.

WAN totals are derived from the WAN statistics counters (`rx_byte_all` + `tx_byte_all`) and must not be mixed with per-device/LAN/WLAN counters.

Statistics reset is a separate destructive counter operation and is not related to the `reset` reboot model.

## Wi-Fi / STA findings

The exact 2.5.94 image contains real Marvell STA/WPS client code and the shipped Wi-Fi payload is from the uAP/STA family. Static work also located station-mode scan/association-related code paths.

However, stock product networking does not expose a complete supported Wi-Fi-as-WAN data path. Later reverse-engineering work showed that a working repeater/WISP implementation requires more than simply exposing the hidden WEBI controls; native STA interface/data-path work is still gated separately.

These findings do not affect the reboot verdict.

## Persistence, NAND and recovery research

Exact 2.5.94 native analysis recovered:

- generic persistent-setting wrappers used by stock code;
- the NAND context/BBT structure and remap table format;
- two direct `BackupFw` calls into the stock flash-read path;
- the IPv4 forwarding/NAT locations used by the separate Community TTL research;
- stock AT/MRD paths used by the separate IMEI research.

Those findings are documented in the Community firmware research artifacts; they are not normal API guarantees and should not be conflated with the stock XML contracts in this repository.

## Security-sensitive surfaces

Firmware contains debug/diagnostic/TR-069-related contracts and native machinery. Their existence does not imply a Unix shell. In particular, Telnet/diagnostic/debug functionality must remain confidence-scoped and firmware-specific.

The project policy remains:

1. read-only discovery can be broader;
2. write mappings require firmware-specific evidence;
3. destructive values are never guessed;
4. normal writes should be read back where possible;
5. restart/shutdown are one-shot operations and must not be blindly replayed after transport loss.

## Scope and limitations

This is the consolidated static analysis of the clean MF885 2.5.94 image at the depth reached by the project: container/partition reconstruction, WEBI/XML inventory, native OSLO reverse-engineering of targeted subsystems, firmware comparison and application-contract validation.

It is **not** a claim that every function in the 9.6 MB OSLO image has been exhaustively decompiled, nor does static confirmation replace observation of every destructive effect on hardware.

For the specific reboot question, however, the evidence is sufficient to move the 2.5.94 compatibility mapping from `unknown` to **firmware-confirmed**.
