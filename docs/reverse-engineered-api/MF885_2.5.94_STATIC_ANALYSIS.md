# MF885 firmware 2.5.94 — static analysis baseline

This document records the reproducible static-analysis baseline for the stock ZMI MF885 firmware used by this project. It separates facts established from the exact 2.5.94 image, companion-client evidence, runtime implementation and assumptions inherited from related firmware.

## Executive conclusions

1. The analysed image is a complete stock MF885 BackupFw image, not a reconstructed approximation.
2. The main runtime is a Nucleus PLUS / Marvell monolithic image (`OSLO`), not a conventional Linux filesystem/userland.
3. The XML/Duster management interface is real native firmware machinery. XML schemas, frontend code and native callback descriptors must all be considered separately.
4. The `reset` model is a **reboot**, distinct from `restore_defaults`, which is the factory-default path.
5. The `poweroff` model is the normal shutdown/power-off path.
6. The earlier GET-versus-POST transport gap is closed by reverse engineering the period-relevant ZMI Android companion client 1.2.42: reboot, power-off and factory reset are one-shot **GET `method=get`** requests with no XML request body.
7. The uploaded English APK is repacked/test-key-signed, so its provenance is recorded separately from an original store-signed APK; the relevant power implementation is in `classes.dex` and explicitly targets the MF885/MF96 Ver.D family.
8. The project runtime is now transport-aware: the dedicated MF885 2.5.94 profile can express GET/no-body power commands independently of the retained 2.5.96 POST/SET mapping.

## 2. Backup container / partitions

The stock BackupFw image uses the ZIMI backup format with a 572-byte header followed by fixed partitions used by the device restore path.

```text
OSLO  0x460000
GRBI  0x0c0000
WEBI  0x1c0000
WIFI  0x080000
WCAL  0x080000
RFBN  0x010000
```

BackupFw/RestoreFw is distinct from the signed Marvell FBF software-update path.

## 3. Runtime architecture

The main OSLO image contains:

- Nucleus PLUS RTOS components;
- Marvell networking/cellular integration;
- forked lwIP networking;
- Mongoose 3.0 HTTP server;
- Digest/session logic;
- Duster XML model dispatch;
- SMS/SIM/APN/cellular management;
- NAT/DHCP/DNS/firewall/routing;
- firmware backup/update/restore;
- CWMP/TR-069/STUN;
- Wi-Fi driver/WPS/client-related code.

Linux-looking strings do not establish a Linux userspace or Unix shell on this build.

## 4. Duster model dispatcher

Exact 2.5.94 analysis established a 0x38-byte Duster descriptor layout with callback slots:

```text
+0x10  pre_set
+0x18  post_set
+0x20  pre_get
+0x28  post_get
```

A schema establishes the XML tree, but not automatically which callback direction causes a side effect. This distinction was the source of the former power-command uncertainty.

## 5. HTTP and Digest transport

Physical management endpoint:

```text
/xml_action.cgi
```

Generic Duster forms:

```text
GET  /xml_action.cgi?method=get&module=duster&file=<model>
POST /xml_action.cgi?method=set&module=duster&file=<model>
```

Digest uses a different logical URI for XML calls:

```text
physical HTTP path  /xml_action.cgi
Digest uri / HA2    /cgi/xml_action.cgi
```

The 1.2.42 Android client independently confirms this split as well as `realm=Highwmg` and `qop=auth`.

## 8. Reboot: `reset`

WEBI schema:

```xml
<RGW><reboot/></RGW>
```

Semantic mapping:

```text
reset -> reboot/restart
```

The Android client resolves the invocation transport. `RouterRebootActivity` flows through `RouterManager`, `RouterApi` and `HttpBasedRouterApi`, which submits:

```http
GET /xml_action.cgi?method=get&module=duster&file=reset
```

with no XML body.

After submission the app polls for the host/router to return. It does not send a second reboot request.

Confidence split:

```text
model exists                         confirmed
reset means reboot                   firmware-confirmed
reset != restore_defaults            confirmed
stock-family client HTTP method      GET, companion-app-confirmed
request body                         none
project runtime transport            implemented
live execution on exact 2.5.94       separate evidence level
```

## 9. Shutdown: `poweroff`

WEBI schema:

```xml
<RGW><shutdown/></RGW>
```

The Android shutdown UI has an explicit confirmation flow and eventually calls:

```http
GET /xml_action.cgi?method=get&module=duster&file=poweroff
```

with no XML body.

Therefore the former GET/SET ambiguity is resolved for the companion-client implementation:

```text
poweroff -> shutdown/power-off
method   -> GET
body     -> none
```

The project runtime now encodes this command in the dedicated 2.5.94 profile.

## 10. Factory defaults: `restore_defaults`

Factory reset is a third, separate command. The Android client invokes:

```http
GET /xml_action.cgi?method=get&module=duster&file=restore_defaults
```

This is decisive safety evidence for the distinction:

```text
reset             -> reboot
poweroff          -> power off
restore_defaults  -> factory reset
```

Never substitute `restore_defaults` for `reset`.

## 11. `trueshutdown`

A `trueshutdown` model/schema exists in the broader firmware family. The analysed APK's ordinary shutdown UI uses `poweroff`, not `trueshutdown`.

Project policy remains:

```text
trueshutdown = unadvertised / distinction unresolved
```

## 12. What “Restart” means in this project

The names at different layers describe one logical operation:

```text
UI label          Restart
client action     reboot
firmware model    reset
firmware semantic reboot
stock-family HTTP GET ...&file=reset
```

There is no separate device operation called Restart in addition to Reboot.

## 13. Runtime implementation

The project now carries transport in the destructive model descriptor rather than assuming every destructive operation is POST/SET.

For MF885 2.5.94 the profile encodes conceptually:

```text
reset:
  method: GET
  file: reset
  body: none

poweroff:
  method: GET
  file: poweroff
  body: none
```

The existing power flow in `scriptable.js` still passes the firmware semantic tree to the API helper, but the transport-aware helper ignores that XML body for a GET descriptor. For the retained 2.5.96 string descriptors, it continues to use the previous POST/SET + XML behaviour.

The API helper also separates destructive submission from ordinary `write -> read-back -> verify`: a destructive command no longer fails merely because no normal verification callback was supplied.

Restart and Power off are therefore enabled for the dedicated `2.5.94` MF885 profile. The one-shot rule remains: do not replay after timeout or connection loss. A live exact-device run remains the final behavioural validation step, not a request-shape discovery step.

## 14. Wi-Fi / STA findings relevant to firmware identity

The exact 2.5.94 image was also used for Wi-Fi reverse engineering. Findings include:

- shipped `sd8801_uapsta.bin`;
- WPS/STA scan/association code and strings;
- `BSS_TYPE_STA` and `BSS_TYPE_UAP` paths;
- product networking that registers the uAP side with lwIP;
- Duster descriptor evidence showing that schema/storage presence is not sufficient to prove an active callback;
- product `mlan_ops[]` registration consistent with UAP-only product operation.

These findings reinforce the same methodology used for power controls.

## 15. Network / cellular findings

The exact raw 2.5.94 image contains the networking/modem paths used by the project's staged research, including:

- IPv4 NAT forwarding path used for TTL research;
- stock AT transport;
- MRD/IMEI-related strings/handlers;
- APN/WAN data-model machinery;
- `status1`, `wan`, and `Engineer_parameter` telemetry.

Modified community-build capabilities are not automatically stock API features.

## 16. Debug, diagnostic and Telnet evidence

The firmware family contains engineering/debug contracts including `debugmodeon`, `diagnostic`, and `control_telnet`.

Their presence does not establish a general-purpose shell. Schema, callback and listening-service evidence must be separated.
